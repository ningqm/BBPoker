# 通用部署说明

此文档使用示例域名与通用目录，不包含任何线上实例、账号或凭据。当前架构是一台服务器、一个 Node.js 进程、一份加密存档；支持最多 10 张活动桌，但仍由单进程顺序写入。

## 1. 本机检查

安装 Node.js 22 或更高版本，在项目根目录执行：

```sh
npm run check
npm test
npm start
```

打开 [http://localhost:8787](http://localhost:8787)。自动测试使用临时数据；正常启动默认把真实使用数据保存到项目的 `data/`。网页后端没有第三方运行依赖，不需要 `npm install`。

## 2. 配置生产服务

复制 `.env.example` 为 `.env`，在服务器上私下填写：

```dotenv
PUBLIC_ORIGIN=https://poker.example.com
HOST=127.0.0.1
PORT=8787
DATA_DIR=/var/lib/bbpoker
TRUST_PROXY=loopback
CLIENT_ORIGINS=
```

将示例域名替换为自己的正式域名。0.7.0 移除了建房口令，已注册并登录的用户每人可创建一张活动桌；加入方式由公开加入或仅限邀请设置决定。不要把真实配置提交到仓库。

提前创建数据目录，使运行服务的专用普通用户拥有读写权限，并限制为仅该用户访问。启动命令：

```sh
node --env-file=.env server.js
```

直接 `npm start` 不会自动读取 `.env`。长期运行需要由部署者设置 systemd 或其他进程管理器的自动启动与重启；不要用 root 身份运行应用。

## 3. 配置 HTTPS

把域名解析到服务器公网地址，开放 TCP 80/443；后端 8787 仅供本机反向代理访问。Caddy 配置示例：

```caddyfile
poker.example.com {
    reverse_proxy 127.0.0.1:8787 {
        header_up X-BBPoker-Client-IP {remote_host}
        flush_interval -1
    }
}
```

安装受支持版本的 Caddy 并配置其常驻运行。确认域名解析、端口和证书签发实际成功后再邀请朋友。HTTP 应转到 HTTPS；API 和事件流不要经过缓存，事件流需要及时转发。

`TRUST_PROXY=loopback` 仅适用于 **Node 实际收到的连接来自回环地址**，且本机代理覆盖 `X-BBPoker-Client-IP` 的情况。其他来源、其他转发头不会自动受信。不要把 `TRUST_PROXY` 扩大成任意来源，也不要在尚未审查的 CDN/多层代理前沿用此设置。

反向代理行为依据 [Caddy 文档](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy)。云厂商选择、域名接入条件和费用由部署者按实际所在地核对；本仓库不代表任何云资源已经购买或合规审核已经完成。

## 4. 可选：单实例 Docker

仓库包含 `Dockerfile` 和 `compose.yaml`。安装 Docker 后复制 `.env.example` 为 `.env`，填写实际 `PUBLIC_ORIGIN`：

```sh
docker compose up -d --build
docker compose logs --tail=50
```

容器端口只向宿主机回环地址公开，仍需通过宿主机 HTTPS 反向代理访问。`poker-data` 持久卷保存加密存档和密钥。不要运行 `docker compose down --volumes`，它会删除数据卷。

Docker 映射端口不代表容器里的 Node 一定看到回环来源。此模板不设置 `TRUST_PROXY`，限流可能按代理地址合并；如果需要准确识别各玩家地址，应先审查实际网络路径并调整架构，不能仅复制直接运行 Node 的回环信任设置。对少量朋友的首期部署，直接 Node 加本机 Caddy 更容易核对。

Docker 镜像构建与自己的云环境仍需实际验证。无论选择何种方式，**同一份存档只能由一个进程写入**，不支持多副本共享写入。

## 5. 数据、备份与升级

- `table.enc` 是加密存档，`key` 是恢复所需密钥；只备份其中一个不足以恢复。加密不阻止同时掌握两者的管理员读取数据。
- 普通重启读取已保存状态。自动续局由服务器统一执行，已保存的下一手时间保留；过期倒计时在第一位入座玩家恢复连接后重新给出 5 秒。当前版本会保留有效的行动截止时间、牌桌结束时间与已用时间牌，不靠重启重新计时；旧记录缺失行动截止时间时才补充计时。鱿鱼的手内玩法锁定、原轮预留与标记保留；重启后对阻塞和到时恢复窗口重新观察，避免依据失真的离线时间结算。程序更新时保留数据目录与密钥，不要用测试数据替换线上记录。
- 数据和程序分目录仍然可能位于同一块盘。误删、磁盘损坏、实例释放或程序缺陷仍会导致数据丢失。
- 仓库不包含自动异地备份。部署者应将匹配的密文、密钥与必要配置备份到服务器之外的私密存储，并定期演练恢复。

简单的一致备份流程：在两手之间结束本场，停止服务，备份整份数据目录与私密环境配置，再重新启动。备份文件不能出现在静态网站目录、公共仓库或公开下载链接中。

恢复前停止写入并保留当前数据副本；使用匹配版本和整套备份启动，检查用户、历史和积分。已经重新开放给玩家后，不能随意恢复旧备份，否则新发生的记录会丢失。数据持续增长时应增加归档或迁移数据库。

## 6. 上线验收

1. HTTPS 证书有效，后端端口不可从公网直接访问。
2. 两个以上独立账号通过邀请同桌，直接入座、BB 带入限制、下注、结算和导出正常，未公开底牌隔离；头像与昵称修改同步给同桌成员。
3. 在真实 iPhone、Android 和电脑上验证切后台、锁屏、切网后重新同步。离开期间当前手继续，行动超时按桌规处理；普通下一手跳过离线者，鱿鱼必要参与者离线时冻结原轮，在线朋友先打普通手，恢复后从下一手继续原轮。
4. 重启后账号、积分、原牌序和历史仍在，行动截止时间和已用时间牌不重置；时间牌按半小时重置；到时有可继续的鱿鱼原轮则延长完成，无法继续则在手后提供 90 秒恢复窗口，超时结清收桌。实际恢复一份私密备份。
5. 用朋友真正所在网络测试连接质量。服务器健康检查或自动化测试不能代替异地真机验收。

该版本没有短信/邮箱找回、多人联合洗牌、第三方安全审计、自动扩容或完整商业运维体系。实验性原生桥接代码不代表可直接发布 App。

## 多牌桌验收

分别用公开桌和邀请桌验证大厅权限；未受邀者只能看邀请制桌的目录摘要，不得获取邀请凭证、成员、底牌或事件流。检验同账号不能两桌同时入座，一桌计时故障不阻止其他桌推进。按实际服务器测试多桌同时全下计算、事件流与持久化延迟；不要启动第二个进程共享同一加密文件。鱿鱼退出、掉线宽限、重连与结算规则见 [进出桌说明](room-lifecycle.md)。
